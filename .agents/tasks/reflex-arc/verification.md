## Observed on live runs — flagged for the online bench/tuning step (item 13)

With the design's INITIAL threshold constants (unchanged this iteration: `MIN_CHARS_BEFORE_FIRST=40`,
`CHECKPOINT_CHARS=240`, `UNSURE_HI=0.70`), the hosted decider sometimes reads an EARLY/short partial
as only borderline-grounded (grounded ~0.44, confidence ~0.55), which the unsure band turns into a
`freeze`. On one on-spec "redirect handler" run this produced a FALSE POSITIVE freeze on a clean
turn (hurts demo beat 5 / AC6's false-positive guard). This is a TUNING matter, not a build defect:
the four offline score_reflex branch tests and the clean-generation offline test all pass (they use
scripted deciders), and the live reflex demonstrably fires correctly on rigged turns (runs #2, #3).
Per the plan, thresholds are INITIAL values tuned on the `tune` split in item 13 (and the final
values written into `decision.py`'s docstring there); they were deliberately NOT changed here to
avoid tuning on reported cases. Item 13 should raise `MIN_CHARS_BEFORE_FIRST` (so the first
checkpoint sees enough code to judge grounding) and/or sharpen the `grounded` option descriptions,
then re-run `./kit bench` and confirm the clean turn PROCEEDS.

## Mid-generation seam decision (design §4.3)

True mid-stream cancellation is LIVE and works: `cancel_signal` + `agent.cancel()` cut Nova's stream
with `interrupted:true` on rigged turns (run #2). The documented post-chunk degradation / the
`REFLEX_MIDGEN=0` kill-switch remain available but were NOT needed. One cosmetic artifact: cancelling
mid-span makes OpenTelemetry log a harmless `Failed to detach context` to stderr; the turn result is
unaffected, and `agent.py` quiets just the `opentelemetry.context` logger so the cut is not drowned
out (behavior-preserving). Documented in `agent/AGENT.md`.

## What was built (recap)

Reflex Arc — a coding agent with an in-flight nervous system. Amazon Bedrock Nova Pro is the slow
cortex that writes/edits code against a fixed URL-shortener spec (`agent/data/spec/`); Strands
Decider 2B is the fast reflex. ONE decider call per check reads one shared state (spec excerpt +
current task + user boundaries + what the agent is doing) and answers five typed questions
(`grounded`, `looping`, `in_scope`, `safe`, `severity`). The agent's own code maps those to four
verdicts — proceed / steer (Guide) / cut (Deny) / freeze (Confirm/held) — with low-confidence
decisive calls routed to a human. Pattern tag: `#guardrails` (one pattern). Two seams: #1
before-action `InterventionHandler.before_tool_call`; #2 mid-generation checkpoints that cancel
Nova's in-flight stream. AgentCore Memory ON (stores boundaries only), Gateway OFF. Full build
detail is in the iteration-1 record above.

## 2. `./kit bench --split tune` (tuning split — NOT the headline)

First tune run (before rewording), 12 cases / 60 decisions:

| | Strands Decider 2B | us.amazon.nova-pro-v1:0 |
|---|---|---|
| Accuracy | 60.0% | 71.7% |

The decider trailed the LLM. Per-question diagnosis from `results.json` showed a systematic
`no`-bias on two questions only: `grounded` 3/12 and `in_scope` 2/12, almost every miss being
`expected=yes` read as `no` (on-spec implementation code mis-read as "invents something" / "off
task"). `looping` 12/12, `safe` 11/12, `severity` 8/12 were already fine.

Fix (option descriptions only — thresholds unchanged, per
`.kiro/skills/decision-pattern/SKILL.md`): reworded the `grounded` and `in_scope` option
descriptions in `agent/decision.py` to (a) accept plain implementation code (local variables,
control flow, standard Python) of a spec-listed function as grounded, and treat a forbidden name
only *mentioned in a comment but not used* as still grounded; (b) treat implementing the current
task's own function — even partially/early — as in scope, reserving `false` for building a
different unrequested feature.

Second tune run (after rewording), 12 cases / 60 decisions:

| | Strands Decider 2B | us.amazon.nova-pro-v1:0 |
|---|---|---|
| Accuracy | 71.7% | 70.0% |
| Latency p50 per decision | 10324 ms | 4608 ms |
| Cost per 1,000 decisions | $0.0350 | $0.4547 |
| Answered alone at confidence >= 0.7 | 27% | 100% |
| Accuracy when confident | 100.0% | 70.0% |

Per-question after reword: grounded 5/12, looping 12/12, in_scope 7/12, safe 11/12, severity 8/12.
The remaining grounded/in_scope misses are all LOW confidence (~0.50–0.69) — the unsure band turns
those into `freeze` (ask a human), which is why accuracy-when-confident is 100%. Tuning stopped
here (two tune runs only) to avoid overfitting; thresholds were left at the documented INITIAL
values (`decision.py` docstring remains accurate).

Per-question accuracy (decider / llm): grounded 0.50 / 0.69, looping 0.875 / 0.75,
in_scope 0.625 / 0.6875, **safe 0.9375 / 0.4375**, severity 0.50 / 0.75.
`sent_to_human_at_threshold`: decider 57, llm 0. `speedup_p50` 0.42 (the LLM is 2.4x faster at the
median on this hosted setup).

Honest reading: on overall accuracy the decider is roughly level with the LLM (68.8% vs 66.2%).
Its real wins are (1) the SAFETY question — `safe` 93.75% vs the LLM's 43.75%, exactly the
guardrail decision that matters; (2) calibrated confidence — 91.3% accurate when confident vs the
LLM's flat 66.2%, routing its uncertain calls to a human instead of guessing; (3) cost — ~13x
cheaper per 1,000 decisions ($0.035 vs $0.4537). On THIS hosted ugmdu endpoint the decider is
SLOWER than Nova at the median (9.9 s vs 4.1 s); the kit's guidance says the decider wins on speed
only when run on GPU/MLX/close to the agent, and we report the hosted latency as-is.
